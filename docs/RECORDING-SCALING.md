# Запись под нагрузкой: управление, ёмкость, оптимизация

Документ про то, как довести запись от «один воркер на VPS» до сотен одновременных трансляций
(например, для проекта NightRecorder — ночная запись большого числа онлайн-событий).
Цифры нагрузки — **оценки по устройству конвейера, а не замеры**: перед закупкой железа измерьте
реальную запись на вашем сервере (раздел «Как замерить»).

## 1. Что уже есть в EduSync

| Возможность | Где |
|---|---|
| Пауза приёма, число одновременных записей, лимит на пользователя — **из админки, без перезапуска** | Админка → записи → блок «Приём записей» (`system_settings`: `recording_paused`, `recording_concurrency`, `recording_per_user_limit`) |
| Очередь по времени: раньше запланированная запись стартует раньше | `claimNextTask` (`ORDER BY scheduled_time, created_at`) |
| Лимит на пользователя (по умолчанию 2): один клиент не занимает все места, остальные не блокируются | `claimNextTask` |
| Понятная причина ожидания: «ещё не время», «нет воркера», «приём на паузе», «лимит пользователя», «все места заняты» | `startStatus.ts` |
| Потолок параллельности и память контейнера | `.env`: `MAX_WORKERS`, `WORKER_MEM_LIMIT`, `WORKER_SHM_SIZE` |

Как это работает: воркер запускает `MAX_WORKERS` «слотов» (`vps-worker-1…N`). Слот работает, только если его
номер ≤ значения «Одновременно записей» из админки и приём не на паузе. Остальные слоты простаивают
и почти ничего не потребляют. Пауза не прерывает идущие записи.

Остановить/запустить сам контейнер из админки нельзя намеренно: для этого веб-приложению пришлось бы дать
доступ к `docker.sock`, а это фактически root на сервере. Пауза + параллельность закрывают операционные
нужды; перезапуск контейнера — `docker compose --profile worker restart worker` на сервере.

## 2. Почему запись через браузер дорогая

Текущий конвейер: Chromium (программная отрисовка) → кадры JPEG через CDP → Node → ffmpeg (MJPEG на вход) →
libx264 1080p/15 к/с. Ориентировочно на одну запись:

- **~1,5–2 ядра CPU, 1–1,5 ГБ RAM**, диск ≈ 2–4 ГБ/час до загрузки в S3.
- Узкие места: отрисовка страницы и JPEG-кодирование в браузере, копирование кадров, кодирование x264.

Но браузер нужен далеко не для каждого источника. Главная оптимизация — **выбирать самый дешёвый способ
записи под тип источника**:

| Тип источника | Как писать | Ожидаемая цена на запись |
|---|---|---|
| Прямой поток: HLS (`.m3u8`), RTMP, RTSP, прямой mp4/flv | `ffmpeg -i <url> -c copy` с сегментированием, без браузера и без перекодирования | доли ядра, десятки МБ RAM |
| Видеохостинги и стриминг (YouTube, Rutube, VK Видео, Twitch, OK и др.) | достать адрес потока через `yt-dlp` / `streamlink` и записать ffmpeg в режиме copy | то же, без браузера |
| Вебинарные платформы с плеером в странице (Bizon365, GetCourse и т. п.) | браузер, но облегчённый (см. §3) | ~0,7–1,5 ядра |
| Zoom / Teams / Meet / Jitsi / BigBlueButton | штатные средства платформы (§4) вместо захвата экрана | зависит от платформы |

**Выбор способа записи реализован** (`server/services/recording/sourceStrategy.ts`):

| Ссылка | Способ | Чем |
|---|---|---|
| `.m3u8`, `.mpd`, `rtmp(s)://`, `rtsp(s)://`, `srt://`, прямые `.mp4/.flv/.ts/…` | `direct` | `ffmpeg -c copy` с нарезкой на части |
| YouTube, Rutube, VK Видео, OK, Vimeo, Dailymotion, Kick, облачные записи Zoom (`zoom.us/rec/…`) | `extractor` | `yt-dlp` (запасной — `streamlink`) → `ffmpeg -c copy` |
| Twitch, GoodGame | `extractor` | `streamlink` (запасной — `yt-dlp`) → `ffmpeg -c copy` |
| Zoom/Jitsi/BigBlueButton/Teams/Meet/Webex (встречи) | `browser` + подсказка про штатную запись | Chromium |
| Вебинарные платформы и всё остальное | `browser` | Chromium |

Как это работает в воркере:

1. По ссылке выбирается способ; он виден в карточке задачи («Способ: …») ещё до старта.
2. `extractor`: адрес потока достаёт `yt-dlp`/`streamlink`; если трансляция ещё не началась — ждёт до 15 минут
   (`STREAM_NOT_STARTED`, затем повтор), в браузер при этом не переходит.
3. ffmpeg пишет поток без перекодирования частями по `max_part_duration`; каждая готовая часть сразу уходит в S3.
   Запись подтверждается по первым полученным данным; поток, который перестал расти 2 минуты, считается
   законченным — сохраняется всё записанное.
4. Если без браузера не получилось **до начала записи** — тот же запуск переходит на браузер (в карточке:
   «Запись без браузера не удалась, переключились на браузер: …»), повторы этой ссылки сразу идут через браузер.
5. Браузерных записей одновременно — не больше `MAX_BROWSER_RECORDINGS`; записи без браузера берутся и тогда,
   когда все браузеры заняты (`MAX_WORKERS` — общее число мест). Если нужен браузер, а он занят, задача
   возвращается в очередь без траты попытки (`BROWSER_BUSY`).

Переменные: `RECORDING_FAST_PATH=false` — всё через браузер, как раньше; `MAX_BROWSER_RECORDINGS`;
`RECORDING_MAX_HEIGHT` (по умолчанию 1080); `YTDLP_EXTRA_ARGS` (например, `--js-runtimes node`, если YouTube
потребует JS-движок); прокси `RECORDING_PROXY_URL` (только HTTP(S)) применяется и к yt-dlp/streamlink/ffmpeg.
yt-dlp и streamlink ставятся из PyPI при сборке образа; образ пересобирается каждую неделю.

Ограничения: часть площадок шифрует поток (DRM) — тогда сработает переход на браузер; ссылки потоков
YouTube живут несколько часов — для очень длинных эфиров возможен обрыв (запись сохранится до него);
запись чужих трансляций допустима только при наличии прав или согласия — учитывайте условия площадок и закон.

## 3. Облегчение записи через браузер (без смены архитектуры)

Настраивается переменными окружения воркера. **По умолчанию в `docker-compose.prod.yml` уже 1280×720 и 10 к/с:**

- `VIEWPORT_WIDTH` / `VIEWPORT_HEIGHT` = `1280` / `720`: в 2,25 раза меньше пикселей, часто достаточно для вебинаров.
- `FRAME_RATE` = `8–10` для слайдовых вебинаров (статичная картинка), 15 — для движущегося видео.
  Для вебинаров с живым видео верните в `.env`: `VIEWPORT_WIDTH=1920`, `VIEWPORT_HEIGHT=1080`, `FRAME_RATE=15`.
- Длина чанка — поле задачи `max_part_duration` (по умолчанию 20 мин); готовые чанки сразу уходят в S3, диск не копится.

Дальше (требует доработки кода, оцените отдельно):

1. **Xvfb + `ffmpeg -f x11grab` + PulseAudio** вместо CDP-скринкаста: меньше копирований, обычно ощутимо
   меньше CPU, нет JPEG-кодирования.
2. Режим кодирования: для слайдов `-tune stillimage`, `-crf 28`; при нехватке CPU — `-preset ultrafast`
   (как сейчас), при нехватке трафика/диска — `veryfast` с большим CRF.
3. Аппаратное кодирование (NVENC/VAAPI/QSV) на серверах с GPU — разгружает CPU, но подходит не везде.
4. Один общий Chromium на воркер с отдельными контекстами вместо нового процесса на запись — экономия
   памяти, но хуже изоляция: сбой одного браузера роняет все записи.

## 4. Платформы со встроенной записью

Не записывайте экран там, где платформа отдаёт запись/поток штатно:

- **Zoom** — Meeting SDK (бот) и RTMS для потоков аудио/видео/транскриптов; в этом проекте доступны
  справочные навыки Zoom.
- **Jitsi** — Jibri (запись на отдельных машинах); **BigBlueButton** — встроенная запись;
  **Teams/Meet** — запись самой платформой или коммерческие API «бот на встречу».
- Если вы сами управляете приёмом потока — медиасерверы **MediaMTX / SRS / nginx-rtmp** пишут сегменты
  без браузера.

## 5. Инфраструктура для высокой нагрузки

**Размер парка** считается от пикового числа одновременных записей:
`ядра ≈ Σ (число записей типа × цена типа)`, `RAM` аналогично. Пример: 100 одновременных браузерных записей —
это порядка 150–200 ядер и ~120 ГБ RAM, то есть **парк серверов**, а не один VPS. 100 одновременных
HLS-копирований — один скромный сервер (но смотрите на сеть).

1. **Разделите роли.** Веб + БД на одном сервере, воркеры — на отдельных. Тяжёлая запись не должна отнимать
   CPU у сайта и PostgreSQL. Воркер «глупый»: ему нужны только БД и S3, поэтому новый узел — это тот же
   compose с другим `WORKER_ID` и своим `MAX_WORKERS` (БД должна принимать подключения с нового IP; не
   открывайте 5432 в интернет — используйте VPN/WireGuard или частную сеть).
2. **Очередь.** Опрос PostgreSQL с атомарным захватом нормально работает до сотен задач. При росте: добавить
   `FOR UPDATE SKIP LOCKED` в захват задачи (убирает конкуренцию воркеров за одну строку); дальше — Redis/BullMQ,
   NATS или Temporal, оставив PostgreSQL источником истины.
3. **Ночные пики.** Многие события начинаются ровно в :00 / :30 — «громовое стадо». Меры: прогрев (поднимать
   браузер/ffmpeg за 1–2 минуты до старта), разброс стартов на десятки секунд, **резервирование мест при
   планировании** (при создании задачи считать, хватит ли ёмкости в это окно, и предупреждать
   пользователя заранее, а не молча ставить в очередь — запись живого вебинара нельзя «догнать»).
4. **Автомасштабирование по расписанию.** Для ночной записи удобно арендовать мощные серверы с почасовой
   оплатой только на ночь: поднять узлы к 21:00, погасить к 08:00. Узлы можно брать «прерываемые» (spot):
   при потере узла задача по heartbeat вернётся в очередь (но запись события при этом прервётся — для
   критичных записей нужна избыточность: два узла пишут одно событие).
   При росте — Kubernetes + KEDA по длине очереди.
5. **Сеть.** Каждая запись — входящий поток (3–6 Мбит/с для 1080p) и исходящая загрузка в S3 примерно того
   же размера. 100 записей ≈ 0,3–0,6 Гбит/с в обе стороны: проверьте порт сервера и **лимиты трафика** тарифа.
   Режим copy сохраняет исходный битрейт и не раздувает трафик.
6. **Хранилище.** Загружайте чанки сразу и удаляйте локальные файлы; настройте правила жизненного цикла S3
   (перенос в холодный класс/удаление через N дней). Склейка чанков (merge) — отдельной низкоприоритетной
   очередью, не на узлах записи в момент пика.
7. **Надёжность.** Переподключение к потоку (`-reconnect 1 -reconnect_streamed 1` для HLS/HTTP), запись в
   сегменты/фрагментированный MP4 (обрыв не теряет всё), watchdog зависших записей (есть), идемпотентные
   повторы (есть), дублирование критичных записей, ограничение числа повторов по источнику (circuit breaker).
8. **Наблюдаемость.** Метрики: задержка очереди (сколько задача ждала после времени старта), доля неудач по
   кодам причин (`start.code` из `recording_tasks.metadata`), число занятых мест, загрузка CPU/RAM/сети по
   узлам, свободный диск. Алерты в Telegram/почту: нет живых воркеров, очередь растёт, доля `NO_FRAMES`/`URL_*`
   выше нормы. Prometheus + Grafana или то, что уже стоит на сервере.
9. **Гео и прокси.** Источники, закрытые для РФ, — через пул прокси/выходных узлов за границей (см.
   `RECORDING-PROXY.md`); для массовой записи прокси должен быть на узел или пул, а не один на всех.
10. **Время.** Сейчас `scheduled_time` хранится без часового пояса, и воркер сдвигает его через
    `SCHEDULED_TIME_TZ_OFFSET_H`. Для «ночных» событий в нескольких часовых поясах переведите колонку на
    `timestamptz` и храните UTC — это отдельная миграция БД.

## 6. Альтернативные технологии (что пробовать)

| Задача | Инструменты |
|---|---|
| Запись потоков без перекодирования | ffmpeg, GStreamer |
| Извлечь поток с видеохостинга/стриминга | yt-dlp, streamlink |
| Захват страницы в браузере | Playwright/Chromium + Xvfb + ffmpeg x11grab; запись вкладки расширением через `tabCapture`/MediaRecorder (кодирует сам браузер, но нужен headful Chrome и расширение) |
| Конференции | Jibri (Jitsi), встроенная запись BigBlueButton, Zoom Meeting SDK/RTMS |
| Если вы управляете приёмом | MediaMTX, SRS, nginx-rtmp |
| Готовые сервисы «бот на встречу» | коммерческие API записи встреч (оценивайте цену за минуту и ограничения платформ) |

## 7. Как замерить на вашем сервере

1. Запустить 1 запись, затем 2, 3 одновременно и смотреть `docker stats myepa-worker` и `top`: CPU и RAM
   на запись.
2. Замерить размер файла за 10 минут (диск/трафик).
3. Проверить, что кадры не теряются: в логах воркера `[WAIT] Прогресс: … кадров` растёт равномерно
   (≈ `FRAME_RATE` в секунду).
4. По результату: `MAX_WORKERS` ≈ min(ядра / цена записи, RAM / цена записи) с запасом 25 %, и такой же
   `WORKER_MEM_LIMIT`.

## 8. Что нужно знать про NightRecorder, чтобы дать точный план

- Сколько событий за ночь и **пик одновременных** записей; длительность одного события.
- Типы источников (доли): HLS/RTMP, видеохостинги, вебинарные платформы, конференции.
- Требуемое качество (720p/1080p, аудио), срок хранения, кто и как получает записи.
- Где живёт проект сейчас (сервер, провайдер, лимиты трафика), есть ли свой код записи и какой.
- Допустимы ли потери части записей и нужна ли избыточность (двойная запись).

Репозиторий NightRecorder из этой сессии не виден (доступ выдан только к `tulubyev/EduSync`); чтобы
разобрать его код, подключите репозиторий к сессии.
